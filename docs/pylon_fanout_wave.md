# Second-wave pylon fan-out

The first commodity registry established a 73-record admitted estate. The congruent-shape atlas then showed that its two largest unmapped implementation surfaces were the scale-seam communication tax and the remote-venue envelope, with causal custody of clocks, traces, instruments, calibration, environment, and accepted output sitting immediately underneath both.

The second wave is a staging area for those surfaces. It is not a silent registry expansion. A candidate remains outside the admitted registry until its source identity, license, adapter, reference fixture, receipt schema, and substitute coverage have been qualified.

```text
public mechanism
        ↓
wave candidate
        ↓
existing pylon and gap projection
        ↓
bounded first transaction
        ↓
reference adapter and fixture
        ↓
receipt and substitution proof
        ↓
explicit promotion into admitted registry
```

The current wave contains 25 candidates across three fronts:

```text
scale_seam       10
remote_venue      8
causal_custody    7
```

All records preserve `dependency_mode=commodity_only`. Every record points to official public sources and reusable assets, projects onto existing pylon and registry-gap identifiers, names its first transaction and required receipts, and carries explicit promotion blockers.

## Scale-seam front

The scale-seam front joins workload traces, analytical models, cycle-accurate models, full-system RTL simulation, workload construction, energy models, mapping models, and thermal models. It includes Chakra, ASTRA-sim, gem5 Garnet, FireSim, FireMarshal, SST, BookSim2, Accelergy, Timeloop, and 3D-ICE.

The intended transaction is not to choose one universal simulator. It is to make all of them consume the same accepted workload and emit compatible seam receipts:

```text
accepted workload and trace
        ↓
tile seam
        ↓
die seam
        ↓
package seam
        ↓
board seam
        ↓
rack seam
        ↓
facility seam
```

Each seam must expose traffic, synchronization, serialization, mapping, utilization, retry, latency, energy, thermal state, occupied allocation, and model identity. The models remain reference twins until measured behavior replaces them.

## Remote-venue front

The remote-venue front joins portable workflow and task APIs, archival packaging, managed research flows, HPC workload managers, browser portals, and regression frameworks. It includes GA4GH WES and TES, RO-Crate 1.3, Globus Flows and Transfer, Flux, Open OnDemand, ReFrame, and CWL.

The intended transaction is:

```text
sealed submission
        ↓
service and venue discovery
        ↓
queue and execution
        ↓
raw returned artifacts
        ↓
local replay
        ↓
accepted result or refusal
        ↓
venue migration
```

A remote dashboard, queue completion, transfer completion, or service response cannot become accepted work. The venue controls only the declared execution envelope. Workload identity, fallback, acceptance, evidence, and historical custody remain local programme authority.

## Causal-custody front

The causal-custody front joins distributed telemetry, full-stack tracing, precision clocks, hardware-test orchestration, instrument frameworks, and experiment plans. It includes OpenTelemetry and OTLP, Perfetto, LinuxPTP and White Rabbit, OpenHTF, QCoDeS, Bluesky and Ophyd, and PyMeasure.

The intended braid is:

```text
workload state
+ device state
+ entropy or path trace
+ environment
+ calibration
+ instrument identity
+ synchronized clocks
+ power and thermal traces
+ accepted output
        ↓
one reconstructable execution interval
```

No single framework receives authority over the causal record. OpenTelemetry may transport semantic telemetry. Perfetto may provide a high-resolution trace and query surface. PTP or White Rabbit may establish clock relationships. OpenHTF, QCoDeS, Bluesky, or PyMeasure may operate instruments and experiments. The receipt must still bind their outputs to one accepted-work interval and retain their transformations and losses.

## Machine-readable interfaces

Generate the full wave report:

```bash
ahead-rev-wave \
  --out artifacts/pylon-wave.json
```

Generate the immediate priority-one transaction floor:

```bash
ahead-rev-wave \
  --priority-max 1 \
  --out artifacts/pylon-wave-priority-one.json
```

Generate one front:

```bash
ahead-rev-wave \
  --front remote_venue \
  --out artifacts/remote-venue-wave.json
```

The `--require-closed-intake` flag deliberately returns exit code `2` while any selected candidate still carries promotion blockers.

## Promotion rule

Promotion into the admitted registry requires six independent closures:

1. A pinned source or specification identity.
2. A reviewed license and access boundary.
3. An ahead adapter or profile.
4. A deterministic reference fixture.
5. A schema-valid receipt and failure fixture.
6. Substitute coverage that preserves the relevant pylons if the actor or programme disappears.

The wave therefore increases search breadth without weakening registry authority. Its control question is: which new public mechanism closes scale, venue, or causal custody while remaining replaceable behind the existing workload, pylon, and receipt authority?
